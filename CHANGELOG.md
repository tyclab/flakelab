## [Unreleased]

### Added

- `flakelab accounts`: several logins per agent CLI on one box, one live per tool, switched without a logout. `add <tool>` snapshots the tool's live login into `~/.local/state/flakelab/accounts/<id>/` (0700 and 0600; an id is never reused; an entry is named by id, alias or label), `switch <entry>` makes a stored login the live one inside one transaction under our own `flock` and the tool's own locks — for Claude Code the `~/.claude.lock` / `~/.claude.json.lock` mkdir protocol its token refresh takes, so a swap can never land inside a refresh; a held lock refuses with exit 2 and changes nothing, a stale one is taken over — writing the outgoing login back into its own entry first, since the tool may have rotated the refresh token since it was stored, or into `unclaimed/` when no entry carries it, so a login is never lost; a failed write restores the previous login. Running Claude Code sessions carry on with their next message. `switch --next <tool>` rotates in id order past disabled entries; `alias`, `disable`/`enable`, `remove` (`--yes`, or a terminal to ask) and `status [--json]`, which also reports a login made by hand as drift. The listing carries each entry's cached windows (`5h 62% · 7d 91% · Fable 40% (3m)`), `--fetch` polls the entries whose plan is due — the active one first, with the live token Claude Code holds and never refreshes here, the others with their stored token, refreshed first when expired and persisted before use — under the usage endpoint's measured budget: 3 minutes for the active entry and 5 for a candidate, halved when the binding window moved, stretched by half when it did not, never past the next reset, `Retry-After` honoured up to 15 minutes, a 6-minute floor for the hour after a 429; a refresh answered with `invalid_grant` quarantines the entry until its credential changes. `switch --soonest <tool>` takes the candidate whose weekly windows renew first, `--best` the most weekly headroom, both after polling what is due, neither ever a spent week. Phase 2 of `accounts.md`; the adapter contract, auto-switch, parallel profiles and the Codex and Kiro adapters follow. `test-accounts` joins `make test` and the flake checks.
- `flakelab accounts run <entry> [-- args]` and `flakelab accounts env <entry>`: a second account in a second terminal, phase 4 of `accounts.md`. The entry gets a home of its own under the store (`profiles/<id>/`, 0700), seeded from its stored login — the credential, and a `.claude.json` with the account, onboarding done, the theme and the user's MCP servers mirrored from the live one — with settings, keybindings, `CLAUDE.md`, skills, commands, agents and, unless `--no-share-history`, the transcripts and prompt history linked from the real home; a link is recorded in a manifest and only recorded links are ever removed, so a profile's own copy of anything is kept. `run` execs the tool on that profile (`CLAUDE_CONFIG_DIR`) with the auth-override variables scrubbed; `env` prints the export and the unsets for `eval` (`--shell sh|fish|pwsh`), `env --unset claude` the line that unpins. The live login is untouched and the two run side by side; on the entry that is the live login both verbs run the tool as it is. A reused profile is validated with `claude auth status` and reseeded when that fails, when its identity drifted or when the store's credential is newer; a token the profile refreshed is harvested back into the store before anything reads it; an entry with a running profile session is never switched onto, removed or targeted by the engine, and its usage is read with the profile's token and never refreshed here. `flakelab sessions` reads the profiles' session registries and transcripts too, so a profile session shows with its id and `--recent` finds what it left.
- The Codex adapter for `flakelab accounts` (`files/scripts/lib/accounts-codex.zsh`), phase 5 of `accounts.md`: `add codex` stores `~/.codex/auth.json` whole with the identity from the `id_token`'s claims (the ChatGPT account id, the email, the plan as the org); an `OPENAI_API_KEY` login is refused as the other auth axis. A running `codex` keeps the token it started with, so `switch` refuses while one runs and `switch --force` goes past them, printing the `codex resume <id>` line for each (the rollout it holds open names the session). Nothing is refreshed here: usage is read through the tool itself, `codex app-server` and one `account/rateLimits/read` in a scratch home seeded with the entry's `auth.json` (never `~/.codex`), camel or snake case, the primary window as the session window and the secondary as the week, a token the tool refreshed on the way copied back into the store; without a `codex` on PATH the endpoint codexctl uses answers instead. A seat the server no longer accepts is quarantined as `seat-revoked` until a fresh login is added. The engine decides for Codex once `flakelab.accounts.autoSwitchTools` lists it, passing over a stored token past its expiry; `run` and `env` work on `CODEX_HOME` with the config and its named profiles, `AGENTS*.md`, hooks, rules, memories, the MCP OAuth store and, by default, the sessions and prompt history linked from the real home, and a `codex` running on a profile is found through its environment.
- The Kiro CLI adapter for `flakelab accounts` (`files/scripts/lib/accounts-kiro.zsh`), phase 6 of `accounts.md`: the login lives in `~/.local/share/kiro-cli/data.sqlite3`, so `add kiro` exports the token row (Builder ID, Identity Center, social or external IdP), the SSO-OIDC device registration and the profile, start-URL and region rows as one JSON document with every value verbatim, and `switch` writes them back in one transaction, the other sign-in methods' token rows removed, a failed transaction rolled back. The identity is the start URL and region (the email `kiro-cli whoami` reports when it answers is the label: an id must be the same offline); an expired stored token is reported as `expired` and a refusal as `unauthorized` with backoff, never a quarantine, since this adapter refreshes nothing; a `KIRO_API_KEY` run is the other auth axis. Like Codex, a running `kiro-cli` keeps its token: `switch` refuses while one runs and `--force` goes past them, printing `kiro-cli chat --resume-id <id>` for each locked session. Usage is the `GetUsageLimits` call the CLI's own `/usage` makes, one monthly window of credits the listing shows and the engine never counts (a month that is out is out until it resets, and an entry with only that window is known rather than unhealthy). `run`/`env` set `KIRO_HOME` to the profile and `XDG_DATA_HOME` to its `share/`, a copy of the live store with the entry's rows, agents, skills, steering, settings and by default the sessions linked from `~/.kiro`; that second variable moves the shell's other XDG data too. `sqlite3` joins the wrapper's PATH and the flake check's inputs.
- `flakelab backup` carries the `flakelab accounts` store as the per-instance `accounts/` category: the roster and one directory per stored login, archived and restored 0700 and 0600 like `~/.codex/auth.json`, a restore keeping a login this box refreshed, an entry gone from the store leaving the payload; the usage cache, the engine's state and log, the profiles and the unclaimed stash stay on the box. `flakelab doctor` gains an `Accounts` section: the store's and the logins' modes, quarantined entries, drift between the roster and each tool's live login (through `flakelab accounts status --json`), and whether the auto-switch timer is scheduled. `flakelab accounts ingest` reads the JSON Claude Code hands its statusline command and turns its `rate_limits` into the live login's cached session and week windows; the statusline command `claudeSettings` writes now tees its stdin into it, so the usage endpoint is never asked for the active entry (a box that already has a `statusLine` keeps it, as before). Phase 7 of `accounts.md`; the backup note `add` printed is gone.
- `flakelab accounts auto`: the engine that switches a tool's live login to another stored one before the live one hits a rate limit, phase 3 of `accounts.md`. One pure jq program (`files/scripts/lib/accounts-auto.jq`) over one document decides per tick: three bars, one per window class (session 85, week 97, per-model week 95; 100 means never move proactively on that window), the costliest window over its bar deciding, week before model before session; a `proactive` trigger when a bar is crossed, `at-limit` when a window is at 100, `failover` after three ticks with the live entry's usage unknown, held instead while the live token merely expired with no session using it; a five-minute cooldown on proactive moves only; candidates with known usage and an unspent week, for a proactive move also under the bar and ten points better than the live entry, ordered by earliest weekly renewal (`soonest-reset`) or most weekly headroom (`best`); the first candidate freshened (a token about to expire refreshed and persisted first, a refused lineage quarantined and the next taken) and switched through the same transaction as `switch`. Every tick logs its events (`poll`, `switch`, `no-switch` with the reason, `blocked`, `quarantine`, `error`) to `auto.log` in the store and, with `--json`, to stdout; `--once` is one tick per tool, `--dry-run` decides without switching, the loop form ticks every `--interval`. `flakelab.accounts.autoSwitchInterval` (default `null`) schedules it as the `flakelab-accounts-autoswitch` user timer; `autoSwitchTools`, `sessionThreshold`, `weekThreshold`, `modelThreshold`, `modelWindows` and `strategy` set the engine's knobs, exported to the script by its wrapper and overridable per run by the flags. While the timer is on for Claude Code, a `Notification` hook on `quota_auto_resume_fired` in `~/.claude/settings.json` runs one tick the moment a session decides to wait for its window, so the reactive case does not wait for the timer; owned by its command like the `SessionEnd` hook.
- `flakelab web`: the dashboard in a browser (`files/scripts/web`, `files/scripts/lib/web.py`, `files/config/web/index.html`), the front end `remote-sessions.md` keeps beside the shell one. One python3 process from the standard library: the page and a JSON API over `accounts` and `claude-sessions`, so every write is one CLI call and the CLI's locks, refusals and exit codes hold. It shows the stored logins with their windows and a switch button, drift, the running sessions with their tmux window, a form that starts one in tmux, the usage poll and the engine's dry run, and a link to the terminal. Bound to 127.0.0.1:8321 unless told otherwise (every-interface binds are refused; the box's WireGuard address is the one to name), every API call behind the bearer token in `~/.local/state/flakelab/web/token`, made on the first start and shown by `--print-token`. `flakelab.web.enable` runs it as the user service `flakelab-web` on `flakelab.web.bind`/`port`; `flakelab.web.terminal` adds ttyd as `flakelab-ttyd`, a browser terminal attached to the `agents` tmux session with the same token as its basic-auth password. `test-web` joins `make test` and the flake checks.
- `flakelab notify`: a push when an agent session waits on you, phase 3 of `remote-sessions.md`. It posts to an ntfy topic the event, the directory and the one line that answers it (`flakelab sessions --attach <id>`, `codex resume <id>`), with the topic URL and token read from `~/.config/tyc/secrets.env` (`NTFY_URL`, `NTFY_TOKEN`) at use time. `flakelab.notify.enable` writes the Claude Code `Notification` hook for the types in `flakelab.notify.events` (permission prompts, idle prompts, an agent needing input, the quota auto-resume events), owned by its command like the `SessionEnd` hook; Codex's `notify` line in `config.toml` is `["flakelab", "notify", "--codex"]`. A hook run never fails its caller; `--dry-run` shows the request, `--title`/`--message` send one by hand. `test-notify` joins `make test` and the flake checks.
- `flakelab.mosh.enable` (default `false`, proxmox-vm only): a mosh-server beside the VM's sshd for a client that roams or sleeps, the UDP range opened by the module; and `files/config/windows/enable-openssh-host.ps1`, the idempotent script that turns on OpenSSH Server on a WSL distro's Windows host, port 22 from the WireGuard subnet only, keys only, the login landing in the distro. Phase 4 of `remote-sessions.md`, on the WireGuard tunnel every box is already on rather than a mesh product.
- `flakelab sessions --recent` also lists, with a state root, the sessions another box synced there and not yet pulled to this one, marked so, and `flakelab sessions` finds a session started by `flakelab accounts run` through the profile's own registry. Phase 5 of `remote-sessions.md`.
- `flakelab.claudeRemoteControl` (default `false`): Claude Code's `remoteControlAtStartup` on a switch of its own, with the four env vars Remote Control's feature flags need removed, so every interactive session is steerable from claude.ai/code and the Claude app without adopting the `claudeAgentDefaults` trust bundle; that bundle still implies it. Off, both the key and the vars are left as the user has them, as before.
- `flakelab sessions --start <tool> [dir] [-- args]` and `--attach [id|window]`: an agent session (Claude Code, Codex or Kiro CLI) hosted in a window of the `agents` tmux session, so it outlives the terminal, the SSH connection or the Windows Terminal tab it was started from; `--attach` joins it from any terminal, through a grouped view session per client so two terminals can look at two windows (the view goes away with its client through a `client-detached` hook, since tmux 3.4's `destroy-unattached` would destroy it before the client attaches). A window's command gets the caller's PATH, so the dashboard's service, with no login environment, starts the tools too. The table gains a `HOST` column naming the window, `--json` a `host` object, and `--open` on WSL attaches each tab to such a window when tmux is on PATH instead of running the tool in the tab. `tmux` joins the package set with `files/config/tmux/tmux.conf` (`programs.tmux`), kept to defaults. The design and the phone path are in `remote-sessions.md`.
- `flakelab sessions` lists Codex and Kiro sessions beside Claude Code's: a `codex` process is identified by the rollout file it holds open (`~/.codex/sessions/<date>/rollout-<stamp>-<id>.jsonl`), a `kiro-cli` process by the locked entry in Kiro's own registry (`~/.kiro/sessions/cli/<id>.json` with its `.lock`) in the process's directory. Saved lines carry a tool column (`<tool>  <dir>  <id>`; a line without one reads as Claude Code), `--resume` prints each tool's command (`codex resume <id>`, `kiro-cli chat --resume-id <id>`), and `--recent` reads Codex rollouts and Kiro's closed registry entries too.
- `accounts.md` and `remote-sessions.md`: the designs for account switching across the three agent CLIs and for sessions reachable from another window, machine or phone, with what to verify before building each phase; `BACKLOG.md` points at both.
- Codex-native permission profiles and app approval defaults under `codexAutoReview`: workspace edits remain sandboxed; network access and sensitive command prefixes use automatic review. `codexEnforcePermissions` enforces the profile, reviewer policy, approval mode and command rules through native managed requirements. One Nix rule list generates both local and managed formats. Exact MCP read grants retain their per-tool approvals and other tool metadata is preserved. `CODEX-PERMISSIONS.md` documents configuration, boundaries and runtime verification; Claude hooks, agents and skills are independent.
- `flakelab backup` carries Codex, matching how it carries Claude Code. The payload's per-instance `codex/` holds `~/.codex/config.toml` and its `*.config.toml` profiles, `AGENTS.md` / `AGENTS.override.md`, `hooks.json` and `hooks/`, `rules/` (where the TUI writes the commands you approve), the user skills in `~/.agents/skills/`, and the two token files: `auth.json` (the ChatGPT login) and `.credentials.json` (MCP OAuth, the file Codex falls back to without a keyring, as on WSL). Configs and tokens are archived and restored 0600 under a 0700 directory. A restore keeps this box's token files, which Codex refreshes in use, and keeps `rules/`, `hooks/` and skills files newer than the backup. With a state root, `~/.codex/memories/` syncs as a memory directory, deletions and tombstones included, but newest-wins with no index merge, since Codex regenerates every file there. Under `stateTranscripts`, `~/.codex/sessions/` rides the transcript sync and its secret gate: grow-only both ways, forks parked, the fork check keyed on the rollout line's `timestamp`. The pull skips a session this box archived or compressed to `.zst`. Sessions never enter the payload, and neither do the installer's package cache, logs or SQLite state.
- The Codex CLI, installed into `~/.local/bin` by its official installer (`flakelab.installCodex`, default `true`), which activation re-runs on every switch: `codex update` is that same installer, and a release already under `~/.codex/packages` is not fetched again. An offline switch defers the install or update rather than failing, the health check asserts the binary, and `flakelab doctor` reports it. The nixpkgs `codex` package was ten minor releases behind upstream when this landed. `bubblewrap` comes with it: Codex's Linux sandbox runs the first `bwrap` on PATH, and without one warns at every start and falls back to a bundled helper.
- `flakelab-switch-result`, installed system-wide, and the `flakelab-activation-result` activation snippet it reads: ordered after every other snippet, the activation records its own `$_status`, the system it activated and its init's start time in `/run/flakelab/activation`, at every switch and every boot — the boot's activation status was dropped by stage 2 and the NixOS-WSL init shim alike. The classifier combines that record with systemd's failed units — services crash-looping after a non-zero exit, which switch-to-configuration counts as failed, and the running user managers' units included — into one verdict and exit code (`applied` 0, `degraded` 4, `activation-failed` 2, `unverified` 3, `reboot-required` 100, or the status of a switch that never activated); ARCHITECTURE.md, "A switch's result", has the contract. `flakelab doctor` reports it for the running system, and `test-switch-result` and `checks.activation-result` cover both halves.
- A `soft_deny` entry in the shipped `claudeAutoMode` default: a tool call that returns the rendered secret files (`/run/secrets/tyc-env`, `~/.config/tyc/secrets.env`, `~/.config/tyc/bw-session`) to the transcript — the `Read` tool, `Grep` with a pattern, or a Bash statement that prints them or a value they define — is a secret published to disk. Sourcing, loading `BW_SESSION`, metadata and key-name-only reads stay routine; it clears when the operator names the file and the one key to show. Prose rather than a deny glob or a hook: a glob cannot tell `source` from `cat`, and neither a glob nor a hook clears when the operator names the read.
- `flakelab sessions --autosave` and its `flakelab-sessions-autosave` user timer (`flakelab.sessionsAutosaveInterval`, default `5min`, `null` for none): the running Claude Code sessions snapshotted for crash recovery, one file per boot (`<host>-autosave-<boot>.txt` beside the saves — in the state root when one is set), rewritten only when the running set changed and never with an empty list, this host's five newest kept. After a crash or a hard reset the previous boot's file is exactly what was open, with no `--save` beforehand; `flakelab sessions --resume` / `--open` take it by default, because with no file named they now skip this boot's own autosave and every other host's.
- `flakelab sessions --recent [hours]`: the sessions that are not running but whose transcript changed in the last `hours` (default 24), newest first, each with the command that resumes it from the last directory it recorded — the window closed by mistake.
- A `SessionEnd` hook in `~/.claude/settings.json` that starts `flakelab-state-sync.service` when a session closes, so a finished session reaches the state root at once instead of after the next timer tick. Written only while the state sync is scheduled and removed again when it is not; recognised by its unit name, so a hand-added `SessionEnd` hook is left alone.
- Session side files sync with the transcripts (`stateTranscripts`): the tool outputs Claude Code spills to `<slug>/<session>/tool-results/` and a subagent's `.meta.json` — what a resumed session points into, which dangled on any other box. Write-once, so each is copied only to the side that lacks it and never again; the pushed copy passes the secret gate as plain text, a reported secret replaced literally, and a file whose secret cannot be matched literally stays on its box (`~/.local/state/flakelab/state-sync/side-files.held`, so it is not re-scanned every run).

- `provision`, `generate`, `init` and `flakelab overlay-gen` leave the overlay as a git repository: initialised, one commit, no remote, `core.autocrlf` off, the commit made through the overlay's own `.gitignore` so the secrets stub and key directory stay out of it. Hand-edits and `-Force` regenerations are diffs from then on; an existing `.git` is left alone and gets no commit. The clone sweep has always excluded the overlay by name, which only makes sense for a repository, and the proxmox-vm bootstrap already clones one — the WSL path now produces the same shape.
- `overlay_url` in `user_data.yaml` (`--overlay-url` for `flakelab overlay-gen`, `flakelab.overlayUrl` in the flake): the overlay's own remote, stated once. The generators add it as `origin` without pushing, `flakelab clone` excludes the repository it names instead of the overlay's folder name (which matched any group repo that happened to share it), a proxmox-vm seed built from the overlay uses it as the bootstrap's `OVERLAY_URL` default, and `flakelab doctor` reports an origin whose branch tracks nothing — the push that never happened.
- `test-nix-update`: an offline suite for `flakelab update`'s pre-flight, with `sudo` shimmed. Wired into `make test` and `nix flake check`.
- `test-nix-doctor`: an offline suite for how `flakelab doctor` reads the flakelab input, against a lock in each shape nix writes. Wired into `make test` and `nix flake check`.
- `GLAB_NO_PROMPT=1` in every login session: glab fails at once with the missing flag named instead of opening an interactive question, which in an agent's terminal-less shell was a hang until the tool timeout. At a real terminal it only skips the confirmation prompts.
- The Claude permissions merge also installs the marketplace's `recommended-ask.json` as `permissions.ask`, asserted whole, alongside the existing `recommended-permissions.json` unioned into `permissions.allow`. Both the activation and `flakelab update`'s replay do it. Asserted rather than unioned because an ask rule prompts even when the operator's own message names the action — it is the one layer `soft_deny` cannot reach — so it is the marketplace's list or nothing, and a union could only grow. The file is optional: a marketplace without one leaves `permissions.ask` alone.
- `test-clone-repos`: an offline suite for the clone sweep — the clone, the fetch and rebase of the checked-out branch, every pre-flight skip, and the default-branch fast-forward — against throwaway repos served over `file://`, with a throwaway key so the sweep's ssh preflight passes without an agent. Wired into `make test` and `nix flake check`.

### Changed

- `flakelab update` says what the flakelab input did instead of "flakelab input updated" on every run. `nix flake update` exits 0 whether or not anything moved, so the old line announced an update that most runs did not make, and the detail nix prints went to a variable only a failure shows. The lock's `flakelab` entry is now read on both sides of the re-lock: unchanged says so with the rev it stayed on, and a move prints `abc1234 → 2495fbe` with how many commits came in — counted in a local clone of the same repo under `~/git` that already has both revs, usually the one the change was merged from. The clone is found by the path its `origin` names after the host, in any of the three URL shapes, matched on whole path segments against the lock's `owner/repo` or a git input's URL, and up to six levels down, so a GitLab subgroup's clone counts too. A tarball input, which locks no rev, is compared by its content hash. Nothing is fetched (an update has to work offline, and someone's working tree is not this command's to move), so a clone that has not seen the new rev yet simply gets the revs without a count, and an input that went backwards is counted the other way and said to have gone back.
- `flakelab update` / `update-all` turn a plain-directory overlay into the repository the generators leave - `git init`, one commit, no remote - instead of printing "git init it to get one" on every run. That shape is what `provision` wrote before the overlay became a repository, and what a hand-made overlay still is, so every box from before that change stayed without history or drift check. Nothing is lost by it: `.git` is added, no file is touched, and it happens without asking like the pull of a clean checkout. It is all or nothing - a refusal, a failed commit or an interrupt leaves no `.git` behind, so the next update simply tries again - and it never touches a `.git` that is already there, readable or not. A refusal is a warning, not a stop: the switch runs. `FLAKELAB_STALE_OK=1`, "rebuild it as it is", also leaves a plain directory plain, which is how an overlay in a folder-synced location stays one on purpose; the tree `nix-update` itself sits in is never adopted. The commit runs with signing and hooks off, so the operator's global git config does not decide whether the overlay gets its history. `flakelab doctor` warns on a plain-directory overlay and runs the same read-only check, so its hint says what the update will do.
- `flakelab.stateSyncInterval` schedules the `--state-only` timer on its own: it no longer needs `backupAutostart`, which now only schedules the daily full payload pass. A box that must not run an unattended payload writer (a proxmox-vm guest whose backup root is a soft network mount, say) can still converge its state root on a timer.
- `flakelab sessions --resume` / `--open` no longer `cd` into a directory this box does not have (a session saved on another machine): the line resumes by id — `claude --resume <id>` finds a session from any directory — and names the missing path, and `--open` starts that tab in the home directory.
- The shipped `claudeAutoMode` default spells out the force-push form in `soft_deny` prose instead of two `Bash()` patterns the classifier never matched as patterns: `--force-with-lease --force-if-includes` to the agent's own branch after the operator named the correction; bare `--force`, a lease without `--force-if-includes`, or any force to the default branch stays blocked even when named. The built-in Git Destructive rule already soft-denies force-push and clears on naming; this fixes what the naming clears into.
- The `permissions.deny` floor written into `settings.json` shrinks from thirteen rules to the two `--mirror` shapes, and `AUTO-MODE.md` documents why. That floor is the one layer neither the auto-mode classifier nor the operator can clear — it is precedence 3 and short-circuits before the classifier — so it is strictly harder than `autoMode.hard_deny`, and the invariant stated above `claudeAutoMode` binds there first: destructive-but-legitimate work belongs in `soft_deny`, where naming the operation and its target clears it. The push rules leave rather than being re-scoped to `main`, because both forges already refuse a rewrite of `main` for every clone, machine and token, and because deny globs match raw command text across `&&` and `|` and into quoted arguments — one of them denied a plain `git push -u` on a `-f` that belonged to a chained `gh pr create --body`. Retired rules are listed in `claudeDenyStale` and subtracted before the union, so a box that already merged them converges instead of carrying them forever.
- `flakelab update` / `update-all` pull a clean overlay checkout that is behind its remote (`git pull --rebase`) instead of asking at a terminal and refusing without one, and the fetch in front of it is `--all --prune`. Uncommitted changes refuse rather than autostash; a conflicting rebase is aborted and refused with the tree restored. `FLAKELAB_STALE_OK=1` is the one override and now covers a dirty tree too. The prompt only ever had one useful answer, and the no-terminal refusal turned every `flakeup` from an agent shell into a manual pull first.

### Removed

- `wsl-open` from the `wsl` target's system packages: the flake's `xdg-open` is the one opener now, and `BROWSER` names it. Upstream has been dormant since 2023-04, nixpkgs still ships 2.2.1, and its `powershell.exe Start` takes three times as long to hand a URL over.
- The `cwsl` alias (`claude` started in the overlay checkout). Never used: Claude Code is opened where the work is, and the overlay is one `cd` away like any other repo. `kwsl` stays for Kiro.

### Fixed

- Codex fleet settings now use `/etc/codex/config.toml`, leaving the user config writable for trust decisions and UI changes. Activation backs up and replaces the previous Home Manager symlink; existing regular user files are preserved.

- An offline switch on a box without kiro-cli or Claude Code defers their install instead of failing the health check on the missing binary. Each installer is fetched with `curl` and piped into `bash`, and without `pipefail` the failed fetch handed `bash` an empty script that exited 0, so nothing was recorded for the health check to excuse the missing binary with. A failed `kiro-cli update` is deferred too rather than warned: it is the network, which the health check treats as deferred work, and the warning failed the rebuild the comment beside it said a stale CLI must not fail. `checks.cli-installers` runs each rendered installer offline.
- `flakelab doctor` checks only the AI CLIs the overlay installs. With `installKiro` or `installClaude` off it still failed on the missing binary; the wrapper now exports the enabled set as `FLAKELAB_AI_CLIS`, and `test-nix-doctor` covers it.
- `flakelab update` names a `git+file:` flakelab input as local again ("only committed content is in this build"), and `flakelab doctor` reports it as a local override instead of "could not read the flakelab input from the lock". Both read the lock's `type` as the URL scheme, but nix locks `git+file:`, `git+https:` and `git+ssh:` alike as `git`, so the local case never matched; doctor also called every remote git input, and a sourcehut one, unreadable. The input is still re-locked to its checkout's last commit, as it has been.
- A transcript whose flagged secret runs across a JSON string boundary is redacted instead of held back forever. gitleaks' private-key rule matches everything between its markers, so on a transcript line it runs out of the string holding the key and on through the keys and values that follow; cutting that span out literally left no JSON, the file was held back whole, and once its findings were ruled there was nothing to review either — two subagent transcripts sat that way for days, warned about on every run as "6 secret record(s) held back" while `--review-secrets` found nothing. Such a line is now redacted string by string: every value that carries a piece of the match becomes `[REDACTED:<rule>]`, key names and the other values stand, and the result is verified to hold no piece. The closing line counts transcripts held back whole separately from records the review can show.
- The `flakelab-state-sync` timer finishes again. Folding transcript conflict copies asked "which copies sit beside this transcript" once per transcript, and each answer listed that transcript's whole folder — quadratic in folder size, and on a Windows mount every entry is a round trip. A state root with three workflow subagent folders (741, 469 and 315 transcripts) cost 1.96 M entry lookups per run, measured at 1.1-1.4 ms each: more than the unit's 30 min `TimeoutStartSec`, so since 2026-09-13 no run reached the push or the pull and transcripts stopped syncing. One walk now names the folders that hold a sync artifact at all, and only those are matched, from that one listing (23 s on the same root). Both legs also stop re-reading every transcript on both sides every run to compare line counts: a count is remembered per file under `~/.local/state/flakelab/state-sync/transcript-lines` and reused while size, mtime and inode are unchanged — a transcript is append-only and every placement is a rename — which takes the comparison from 4 min 43 s per pass, twice a run, to under a minute, and keeps it off the corpus size that an unlimited retention grows without bound.
- Keys, `secrets.env`, the provisioning config and the `flakelab backup` payload no longer live inside the overlay. They sat under `<overlay>/files/config`, git-ignored - and `flakelab update`, its re-lock and `setup-wsl-nix.ps1` hand nix the overlay as `path:`, which copies the WHOLE directory into the world-readable store whatever `.gitignore` says: one copy per changed update, the SSH private key, the merged zsh history and the payload included, against the README's "nothing secret lives in the Nix store in plaintext". They live in `<overlay>-payload` now, beside the overlay on the same mount: `flakelab.backupRoot` defaults to `${repoPath}-payload` and fails to evaluate when pointed inside `repoPath` (`payload-outside-overlay` flake check), `setup-wsl-nix.ps1` reads and writes keys, `secrets.env`, `user_data.yaml` and the restore payload there (`status` shows the root), and `nix-overlay-generate` creates the key directory and the secrets stub there. **No migration**: an overlay still in the old layout is named on every `flakelab update`, by `flakelab doctor` with the one `mv`, and by `setup-wsl-nix.ps1` with the `Move-Item` line; then `nix-collect-garbage` drops the store copies already made, and a key that was in them is worth rotating on a shared box. The template `.gitignore` keeps its `files/config/` rules so an old-layout overlay still cannot commit them.
- `setup-wsl-nix.ps1` switches from `path:<overlay>#default`, spelled out, as `flakelab update` does, and the generator's printed steps name the same. A bare path to a directory that is a repository means `git+file:` - tracked files only: not the `flake.lock` the template keeps untracked, not a module not yet `git add`ed - and overlays have been repositories since the generators started leaving one.
- The overlay's first commit can no longer carry a key through a stale `.gitignore`. `setup-wsl-nix.ps1`, `flakelab overlay-gen` and now `flakelab update` all KEEP a `.gitignore` that is already in the overlay and then commit through it, so one from before a template entry existed - or one that never was the template - put `id_ed25519`, `secrets.env` or the backup payload into the commit; the PowerShell path did not even check `git add`'s status. All three now measure first (`files/scripts/lib/overlay-git.zsh`, `Get-OverlayGitLeaks` in the script): what a first `git add -A` would stage is listed from a scratch git dir, without staging anything or creating a `.git`, and whatever the shipped template `.gitignore` ignores is a leak - the paths are named, nothing is committed, the overlay stays as it was. Only the checked list is staged. One exception, because the README documents it: a re-included sops dotenv (`!secrets/secrets.env`) passes when every value in it is `ENC[…]`, the MAC and version are present and every `sops_` key is one sops writes; one plaintext line and it is refused like any other. Since the template is the measure, it now covers what it missed: `files/config/user_data.yaml` (the provisioning config `setup-wsl-nix.ps1` parks in the overlay, tokens in cleartext), every `id_*` key name with `!id_*.pub`, `.env` files and `.claude/settings.local.json`. `nix-update`'s hand-kept name list, which refused that documented file, is gone.
- The overlay template's `!files/config/shared/ssh/keys/.gitkeep` never took effect: git does not look inside an excluded directory, and `files/config/shared/` excluded it, so a cloned overlay had no key directory. `shared/` is now excluded level by level with the one path down to `.gitkeep` opened again; nothing else under it is tracked, and the generator suite asserts exactly that.
- `gh auth login` and `glab auth login` no longer end in `could not lock config file '~/.gitconfig': read-only file system`. Their last step writes the git credential helper with `git config --global`, and both `~/.gitconfig` and `~/.config/git/config` are store symlinks here, so the write failed and every https push asked for a password the CLI already held. The rendered git config now declares the helper itself for `https://github.com`, `https://gist.github.com` and `https://gitlab.com`, in the shape the CLIs write: an empty `helper` first, which resets the list so a general `credential.helper` an overlay adds is never handed the forge token, then `!<store path> auth git-credential`. The login's "Authenticate Git with your … credentials?" question can be answered either way; a self-hosted GitLab is the same stanza in the overlay. The `forge-credential-helper` flake check reads the rendered file back through git.
- Browser logins from a CLI that ignores `BROWSER` open on the `wsl` target. kubelogin — and k9s behind it, where the error is hidden and the TUI just hangs — execs `xdg-open` by name, as does the draw.io MCP server for every diagram, and the target shipped only `wsl-open` plus `BROWSER=wsl-open`, so it failed with `exec: "xdg-open,x-www-browser,www-browser": executable file not found in $PATH`. The target now installs an `xdg-open` (`files/scripts/xdg-open`) that hands a URL, a `file://` URL or a path to `rundll32.exe url.dll,FileProtocolHandler` over interop, query string and `#fragment` intact, with xdg-open's exit codes and the URL in the message when interop is down. A URL past the 32767 characters CreateProcess takes — a large draw.io `#create=` diagram — travels inside a short-lived redirect page under `$XDG_RUNTIME_DIR` instead. `flakelab doctor` fails when no `xdg-open` is on PATH, and `test-xdg-open` covers the script.
- A switch's exit status is no longer read as its result. switch-to-configuration exits 2 when the activation script failed and 4 when a unit failed, and a unit failing after a failed activation overwrites the 2 with the 4 — so every caller guessed, and each differently: `setup-wsl-nix.ps1` died at switch 1/2 on any 4, leaving a distro with the system generation and no user state (a fresh import's first switch starts the lingering user's `user@1000` at once, and that start can fail with `Failed to spawn executor: Device or resource busy`); `flakelab build-distro` discarded the image and its verification on the same 4; `flakelab update` skipped every post-switch step on it; and `flakelab-bootstrap` wrote its one-shot marker over it as "activated, with warnings", a failed activation included. All four now act on `flakelab-switch-result`'s verdict with one rule — applied and degraded carry on, degraded closing with exit 4 and the units named, everything else stops with its own code. `setup-wsl-nix.ps1` reads it after each switch, for the boot its restart starts and at the close, carrying the units a degraded verdict named across switch 2/2, which resets failed units without starting them all; `flakelab-bootstrap` exits 4 on a degraded switch so the unit shows failed, and leaves no marker on anything worse so the next boot retries.
- `setup-wsl-nix.cmd <args>` passes the script's exit code on. Its `exit /b %ERRORLEVEL%` sat inside the `if ( … )` block that runs PowerShell, and cmd expands `%ERRORLEVEL%` when it reads the block, so the wrapper exited 0 even when the script threw.
- A failed `setup-wsl-nix.ps1` switch no longer leaves its root-owned `flake.lock` in the overlay. nix locks before it builds, but the cleanup ran only after a switch that succeeded, so the operator's next `nix eval` or `nix flake check` there died on `Permission denied` as soon as it rewrote the lock.
- `flakelab update` takes back an overlay `flake.lock` it cannot write. Root writes the lock whenever its switch has to lock — on the first update after `setup-wsl-nix.ps1`, which deletes the lock after provisioning, or after a failed re-lock — and from then on the unprivileged re-lock of a `path:` flakelab input failed with `Permission denied`, so the switch evaluated the previously locked snapshot: silently while it was still in the store, and as `NAR hash mismatch` once it was collected. The lock is now copied back to the caller before the re-lock and again after the switch, failed or not — pins unchanged, without sudo, a symlinked lock left alone. When it cannot be taken back and the re-lock of a `path:` input fails on it, the switch is refused and names the `sudo chown` that fixes it, instead of building the stale snapshot; any other input only warns, as before.
- Script output no longer rewrites the data it prints. `print -P` prompt-expands its whole string and `print`/zsh's `echo` read backslash escapes, so a `%` or a backslash in a path, a branch, a URL-encoded hash or a command's error text came out altered: `%3D` in a narHash printed as the date, `%B` turned bold, `C:\Users\…\temp` lost its `\U` to a NUL and its `\t` to a tab, and `flakelab doctor`'s CRLF hint printed a carriage return where its `sed 's/\r$//'` belongs, so the pasted fix did nothing. Worst in `flakelab clone`: a `\c` in git's error text ended the result-ledger record early and glued the next repo's record onto it. Colour is now the only markup — `nix-update`, `build-dev-wsl-nix` and `test-provision-nix` print through a `_say` that escapes `%`, the `nix-doctor` and `nix-backup` log helpers escape their message, and every data-carrying `print`/`echo` in those scripts, `clone-repos`, `activate-hooks`, `glab-group-projects`, `report-stale-repos` and `get_current_wsl_distro_name` is `print -r`.
- `flakelab sessions` counts sessions, not processes. One session open in two processes — `claude --resume <id>` on a session that is already running, or a reattach — registers both pids under the same id, so `--save` and the `--autosave` snapshot wrote the pair twice, `--resume` printed the same command twice and `--open` opened two tabs onto one session (seen on tycdev, one id under pids 303975 and 531229). The saved shape is now one line per session id, taken from the oldest of its processes, and `--resume` / `--open` also collapse a duplicate they read from an existing file. The table and `--json` still list every process, because those report a pid.
- The transcript sync no longer destroys a forked session. Grow-only by line count took any longer copy for the newer one, so a session carried on on two boxes — or resumed from a stale copy — silently lost its shorter branch at the next sync. A longer copy that does not continue the one it would replace (the shorter copy's last `uuid` is not in it) now parks the other branch first — under `<stateRoot>/claude/diverged/` for a state-root copy, `~/.local/state/flakelab/state-sync/diverged/` for a local one — and a transcript conflict copy that forks its base is parked instead of folded away. `claude --resume <parked file> --fork-session` reopens a parked branch.
- Syncthing's in-flight temps (`.syncthing.*.tmp`, `~syncthing~*.tmp`) and folder metadata (`.stfolder`, `.stversions`, `.stignore`) count as sync artifacts: never mirrored into `$HOME`, never synced as state.
- `kiroMcpMerge` no longer aborts the switch when the Claude marketplace clone is absent. Home Manager activates under `set -eu -o pipefail`, so the unguarded `find` over `~/.claude/plugins/marketplaces` failed its command substitution and took the whole activation down before the empty-object fallback on the next line could apply — on every first switch, where `installClaudePlugins` defers until provisioning has seeded a key, and on any box with no marketplace configured. A manifest `jq` cannot read now warns through flakelab-warn and keeps the definitions from `mcp.nix`, so bad runtime data is named by the health check instead of aborting the entry silently. `checks.kiro-mcp-merge` runs the rendered activation entry against an absent, empty, valid and malformed clone.
- `~/.kiro/settings/cli.json` is a forced Home Manager link. `kiro-cli settings <key> <value>` saves by rename, which replaces the link with a regular file; Home Manager moved that aside to `cli.json.hm-bak` once and then failed the next activation, whose backup would have clobbered the first ("would be clobbered by backing up"). The checked-in baseline owns every key, so the switch now restores it instead. In the same release, `flakelab update`'s fetch warning names the checkout it could not fetch — on an overlay-driven box that is the overlay — instead of always blaming flakelab.
- Claude Code, its marketplaces and Kiro keep updating themselves; nothing here pins them, and three switches could stop that unnoticed. `autoUpdates` is asserted `true` in `~/.claude.json`: Claude's native installer writes `false` there to fence off the legacy npm updater, after which only its `autoUpdatesProtectedForNative` flag keeps native updates running. `autoUpdate` is set for every configured marketplace, because Claude defaults every marketplace but Anthropic's own to off — so a marketplace and its plugins moved only on `flakelab update`. And Kiro's baseline `cli.json` states `app.disableAutoupdates: false`. `checks.claude-auto-updates` runs the rendered entry against absent, populated and malformed state.
- `setup-wsl-nix.ps1` and `files/config/secrets.env.example` name `SYNOLOGY_URL` and `SYNOLOGY_VERIFY_SSL` as the non-secret Synology keys; the host/port/https triple they still listed gates nothing since the URL contract.
- The Synology MCP wrapper (the Kiro fallback in `nix/home/mcp.nix`) refuses to start a 2FA account when `XDG_RUNTIME_DIR` is unset instead of writing the settings file — DSM URL, user, password and device token — under `$HOME/.cache`, which is ext4, not the tmpfs the comment promised. Same fix as the marketplace plugin's own wrapper (mcp-synology 2.0.2).
- The provisioner's ssh-agent load reports an empty agent as a failure. Its payload already ends by probing `ssh-add -l`, but printed `AGENT: empty` and exited 0 anyway, so `Add-SshKeyToAgent` returned `$true` against its own contract and `Invoke-Bootstrap` ran the second switch into an agent holding nothing — the SSH steps deferred again, silently, and the "log in once and run `flakelab update`" warning that exists for this case never printed. The probe now sets the exit code: an agent that dies between the `ssh-add` and the probe, or a `KEYDIR` none of the declared keys is readable from, fails the load.
- The proxmox-vm target links `/bin/bash` (tmpfiles, like NixOS-WSL does on the WSL distro). The clones hardcode it — `SHELL := /bin/bash` in Makefiles, `#!/bin/bash` in the Claude statusline — so on a PVE guest `flakelab activate-hooks` failed the hook install for those repos and the statusline never ran, while the same overlay was fine on WSL.
- The flakelab user lingers (`users.users.<name>.linger = true`), so `user@<uid>` and the ssh-agent it hosts survive the end of a session. Each `wsl.exe -u <user> -- …` is its own logind session and the user manager stopped shortly after the last one ended, taking the loaded key with it: the provisioner's second switch could not reach the key `-SshPassphrase` had just loaded, the clone sweep forked a passphrase prompt per repo, and the backup timer never fired without a live session.
- `clone-repos` runs ssh in `BatchMode`: with `--max-jobs` workers a passphrase prompt per repo landed on one terminal, and no tty test could suppress them. It now refuses up front, in one line, when the key is encrypted and the agent holds nothing, and falls back to the user agent's fixed socket when `SSH_AUTH_SOCK` is missing from a non-login invocation.
- `flakelab update` / `update-all` no longer treat an overlay that is not a git checkout, or has no remote, as an unverifiable tree. The pre-flight ran `git fetch` in whatever `repoPath` named: on the plain directory `provision` wrote that was `fatal: not a git repository`, retried after a 2 s sleep, then a "rebuild anyway?" prompt at a terminal and a refusal without one (`FLAKELAB_STALE_OK=1` to get past it), followed by advice to run `git remote set-head origin -a` on a directory with no origin. Both shapes now get one info line and the switch; uncommitted changes in a remote-less repository are still warned about. A checkout with a remote keeps the drift check unchanged.
- `setup-wsl-nix.ps1` treats a sops-enrolled overlay as configured: the status line reports `sops: <path>` instead of `secrets.env : MISSING`, and the up-front provisioning check and the post-seed report no longer count the plaintext seed as missing or print instructions to hand-write it. `nix-doctor` learned this at the cutover; the provisioning script did not, so on an enrolled box every `status` reported MISSING and `provision` opened with instructions to re-create exactly the file the cutover retired (flakelab-config, enrolled 2026-09-03; observed 2026-09-06). Detection is the overlay flake's `sopsSecretsFile`, anchored so a commented-out switch still reads as not enrolled.
- The kiro-plugin clone and the Claude marketplace fetch use the first `sshKeys` entry that exists on disk as their `ssh -i` identity, instead of the first entry's literal name. A box carrying only a later entry — tycdev, with the deploy key and no personal key — deferred both on every rebuild although the clone would have worked (2026-09-02).
- `flakelab update` also updates an installed Claude plugin whose version in the freshly fetched marketplace differs from the installed one, after each successful switch (plugins a marketplace ships from its own tree; externally sourced ones stay with activation). `claude plugin update` lived only in home-manager activation, which is skipped when the built config did not change, and `plugin install` is a no-op on an installed plugin — so a plugin release merged after the last config change stayed on its installed version through every no-op switch, with the freshly fetched marketplace clone already at the new one (observed 2026-09-02: marketplace at skills 13.2.1, cache at 13.2.0). Failures warn and never fail the update.
- The state sync's memory index merge keeps one line per memory file instead of an exact-line union: a hook edited in place replaces the old line, and a file's line follows the file — the side whose copy the mirror just placed wins it, a kept copy keeps its own. The union had let every rewritten hook survive beside its replacement — 854 lines for 171 memories on one box's 2026-09-10 read, so sessions loaded only part of the index.
- The state sync's memory mirror is newest-wins: a topic file the destination changed since the last sync is left alone (`Kept N newer file(s) untouched` in the log) instead of being overwritten by the other side's older copy, so a memory rewritten between a run's push and its pull no longer comes back in its old version.
- The state sync propagates memory deletions. A box records the topic files it holds after each pull; a file it then lacks while the state root still has it was deleted there, so it leaves the state root and a tombstone (`<slug>/memory-tombstones/<file>`, dated the box's last sight of it). Every box drops a copy no newer than the tombstone, a copy edited after the deletion lifts it, and the index drops the line of a file that exists on neither side. A memory directory with nothing left in it, index included, propagates nothing and is refilled by the pull. Before this, the state root's or another box's copy wrote every deleted memory back on the next tick.
- The clone sweep fast-forwards a default branch that is behind, even when the checkout itself cannot move. It only ever rebased the checked-out branch, so a clone parked on a feature branch — or dirty, or detached, or on a branch whose remote was pruned — kept an outdated default branch until someone ran `gitchecker`, which its own output admitted ("default branch NOT updated"). The move is `git fetch . <upstream>:<branch>` through the same helper `gitchecker` uses: it writes the ref alone, never a working tree, and git refuses it unless the move is a fast-forward and no worktree holds the branch — both of which are now reported rather than attempted.
- A switch that builds the same generation re-runs the activation instead of leaving it alone, and both `flakelab update` and `setup-wsl-nix.ps1`'s second switch say what activation still deferred. `nixos-rebuild switch` restarts `home-manager-<user>.service` only when the generation changed, which is exactly the fresh-provision shape: switch 1 defers the git@ steps for want of a key, the key is seeded, and switch 2 builds the same closure and never re-runs them — a green provision whose kiro-plugin checkout, marketplaces and plugins are all missing. `flakelab update` compares the unit's start timestamp across the switch — the one systemd moves on every start, so a restart the switch made and saw fail is not run a second time — and restarts it when it did not move and there is something to re-run: steps the last activation recorded as failed (`activation-failures`, which `flakelab doctor` answers with "Re-run: flakelab update") or deferred, or a unit that is not in effect — failed, inactive, or not activated at all this boot. With both logs empty and the unit active the restart is a no-op, so it is skipped rather than announced, and the line says only what the timestamp shows ("the switch left … alone"): an unmoved stamp means that unit did not change, which a generation that changed elsewhere in the system leaves true, so it never claims the generation is unchanged. The provisioner restarts it outright, at the one moment the agent verifiably holds the key. `flakelab doctor` now also reads `activation-deferred` — it read only `activation-failures`, so deferred work was invisible in the one command that exists to find it.
- The GitLab group discovery skips a project with no commits (`empty_repo`). `flakelab clone` cloned it into an empty checkout and then reported it as `empty repo — no commits upstream yet, skips on every run` on every run afterwards, which is exactly what it says: noise that never resolves itself. It is simply not cloned until someone pushes a first commit, and arrives as an ordinary clone on the next sweep after that.
- `flakelab backup` no longer calls a file that was written while it ran a corrupt copy. The verification compares every copied file against its source, and anything appended in between — a shell history, an opt-in transcript, any file a live session holds open — differed from a copy that was complete when it was taken, which failed the whole run with `Verify mismatch`. A source newer than its copy is now copied once more and compared again; a copy that still differs is still the finding, and a genuine short write leaves both sides at the same mtime and is reported exactly as before.
- A restore no longer writes `~/.claude/plugins/known_marketplaces.json`. The activation owns that file (`claude plugin marketplace add`), and the payload deliberately carries no plugin cache to go with it — so a copy from another box registered marketplaces whose clones are not on this one, and the next activation took the update path for a clone it never made, deferring the plugins behind it. Same reason `~/.kiro/settings/mcp.json` is not restored either.
- `flakelab doctor`'s git-config check asks about the user's configuration instead of the caller's directory. It resolved `user.email` with a plain `git config --show-origin`, so running the doctor from inside a clone that sets its own `user.email` — an ordinary thing for a repository to do — reported that repository's `.git/config` as shadowing the flake, and the remedy it printed (`mv <repo>/.git/config <repo>/.git/config.pre-flakelab`) would have taken the clone's remote, branch tracking and credential helper with it. The probe is `--global` now: a repository's own keys are its business, and a real user-level file shadowing `~/.config/git/config` still fails the check.

### Fixed

- The Proxmox seed's `flakelab-bootstrap` folds `OVERLAY_KNOWN_HOSTS` into the bootstrap user's own `~/.ssh/known_hosts` after the clone. The bootstrap trusted the overlay host through that file alone, so a day-two `flakelab update` — which fetches with the default known_hosts — died on "Host key verification failed" with the deploy key in place, and the guest stayed parked on its bootstrap generation (tycdev, 2026-09-02).

Its lines were all already merged, so nothing was lost; the copy just never went away.
- `flakelab sessions --open` no longer reports `wt.exe failed` for the first session it opens: the tab counter's post-increment evaluated to zero on that pass and fell into the error branch although the tab had opened. The count was right, the line was noise.
- `flakelab update` waits for the distro's own boot activation before switching (bounded, 180s by default via `FLAKELAB_BOOT_WAIT`; `FLAKELAB_BOOT_OK=1` skips the wait). WSL starts `home-manager-<user>.service` at boot and it runs for a minute or more; a switch typed into that window stopped and restarted the unit, and the login session the caller sat in was torn down in the same reshuffle — the terminal went silent at "setting up /sbin...", the switch exited 4 with two failed units, and the operator had to redo it from a fresh session (observed 2026-09-02). Only `starting`/`initializing` and an `activating` home-manager unit are waited on; a `degraded` boot is finished and proceeds.
- New WSL sessions no longer stall 10 s on a VM whose memory has fragmented: `vm.compaction_proactiveness` is raised to 60 (kernel default 20) on every target, so kcompactd keeps the 512 KiB contiguous block a session's Hyper-V socket ring needs available instead of letting the allocation fail into the vsock accept timeout (seen on TYCBOOKELITE 2026-09-02 after a day of memory pressure).
- `gitchecker` skips a repo it cannot check — no origin remote, or one on a forge it does not integrate with — instead of aborting the whole sweep (#40). One vendored clone or a never-pushed `git init` under a scanned root took every other repo's report down with it. Such a repo is reported as `skipped: <reason>` and counts as attention; a fetch or forge-API failure still aborts, because only those put the rest of the sweep in doubt. `gitcleaner` already worked this way.
- `flakelab update` now refreshes every registered Claude plugin marketplace and replays the recommended-permissions merge after each successful switch. Both previously lived only in home-manager activation, which re-runs solely when the built config changed — but the marketplace clone is runtime data, not a build input, so a merged marketplace change under an unchanged system config never reached `settings.json` (observed 2026-09-01: a permissions update sat in the clone through two switches). Refresh or merge failures warn and never fail the update.
- The transcript redactor survives what the scanner actually reports (#36): overlapping length-variants of one token (each its own fingerprint) and exact-duplicate findings made the sequential literal pass fail lines that were fully redacted — every affected transcript was held back whole and a `delete` ruling could never complete. Findings are now deduplicated and applied longest-needle-first, and a needle missing from its line passes only when it sits inside a longer needle already replaced there; every other miss still refuses the write. The scrub path additionally re-scans the candidate and refuses if the ruled fingerprint survives.
- The ssh-agent survives activation with its keys: the same `X-RestartIfChanged=false` pair the backup units carry now guards `ssh-agent.service`, whose unit file changes on every package bump — the default restart silently emptied the agent mid-session until the next interactive login re-prompted. The reloaded definition applies when the user manager next starts.
- Both backup oneshots carry an explicit `TimeoutStartSec` (2h full, 30min state-only): with activation never clearing them, a wedged run would park the unit in `activating` and block its own timer forever.
- ARCHITECTURE.md no longer claims the daily timer "keeps both sides converging": the daily pass only pushes; automatic two-way convergence is `flakelab.stateSyncInterval`'s `--state-only` timer, and pulls otherwise happen only through a manual `--restore`.
- Home-manager activation no longer waits on, stops, or restarts the backup oneshots: both units carry `X-RestartIfChanged=false` (in `[Unit]` for sd-switch and `[Service]` for switch-to-configuration), so a switch that overlaps a running multi-minute sync cannot time `home-manager-<user>.service` out any more — and cannot kill a sync mid-copy. A changed unit definition takes effect at the next timer fire instead.
- Transcript staging is incremental: only a transcript whose source outgrew its synced copy (or has none) is copied into the staging tree and gitleaks-scanned. A quiet run stops re-scanning the whole corpus — which had grown into the multi-minute runs that made the activation timeout above reachable in the first place — and the run logs the phase's staged/unchanged counts and elapsed seconds. A transcript held back whole stays staged every run until a ruling frees it; a partially-redacted one stops re-warning about already-held findings until it grows.

- A `d` answer in `--review-secrets` records the delete ruling immediately instead of only after every record was scrubbed: a record in a file that refuses a rewrite (a live session's transcript, an unwritable history) now stays held as a pending delete that every later review retries — and the ruling reaches the other machines. Before, the failed scrub silently left the old decision standing.
- `flakelab doctor` no longer warns about "0 secret findings held back": the held list can legitimately be a newline-only file after pruning, and the check now counts records instead of bytes.

- Transcript sync is recursive: subagent transcripts live below the session file (`<slug>/<session>/subagents/*.jsonl`) and the one-level globs in the push, pull and restore legs never saw them. A sync-artifact path segment (`@eaDir`, a conflict-named directory) keeps its whole subtree out of every leg.
- Conflict-copy pairing understands the naming the deployed Synology Drive actually produces: the marker is inserted BEFORE the extension (`MEMORY_<host>_<date>_Conflict.md`), which the full-name prefix match could never pair — such copies were excluded from mirrors but their lines were silently lost. The append-after-name shape keeps working, and the pairing still folds dotfile conflicts (`.zsh_history_merged_…_Conflict`).
- Transcript conflict copies are folded grow-only before both legs and then removed: a copy is the other machine's gated write that lost the rename race, so folding stays inside the state root and needs no rescan. Until now they were skipped forever and accumulated beside the file they shadowed.

### Added

- `flakelab sessions`: the Claude Code sessions running in this distro, with the session id Claude Code itself registers per process in `~/.claude/sessions/<pid>.json` (a live `claude` process with no registry file falls back to the transcript it holds open in `/proc`; the newest transcript in a directory is never it, two sessions in one directory share that). `--save` writes `<dir>  <id>` lines to the state root when one is configured, else `~/.local/state/flakelab/sessions/`, so a `wsl --shutdown` or reboot costs nothing but the restart; `--resume` prints the `cd … && claude --resume <id>` lines back, one per terminal; `--open` gives each its own Windows Terminal tab instead, because those lines pasted into one shell run in sequence. Born on 2026-09-02, when a stack reset on a tower needed a reboot and six shells had no known ids.

- `flakelab.sopsSecretsFile` (default `null`) and `flakelab.sopsAgeKeyFile` (default `/var/lib/sops-nix/key.txt`): opt-in sops-nix secrets. The overlay commits ONE age-encrypted sops dotenv file — the encrypted twin of `~/.config/tyc/secrets.env` — and sops-nix decrypts it at activation into the `/run/secrets` ramfs (`tyc-env`, mode 0400, owned by the login); the zsh init prefers that render and falls back to the legacy home file, so un-enrolled boxes are untouched. Only ciphertext ever reaches the repo, the store, or a backup; the one plaintext at rest is the host's age identity, whose path `sopsAgeKeyFile` can point at a disk image backups exclude. Keys are never auto-generated: enrolment is explicit (`age-keygen`, add the recipient to `.sops.yaml`, `sops updatekeys`), and a missing key fails the activation loudly instead of minting an identity the file was never encrypted to. `sops` and `age` land in the system packages on enrolled boxes; `flakelab doctor` reports the render's presence; the `sops-optional` flake check pins the render contract on and off.
- Slug manifests and `flakelab backup --state-gc`: every backup/`--state-only` run records the Claude project slugs this box holds in `<stateRoot>/.flakelab-state-manifests/<instance>`, and `--state-gc` lists the state-root slugs no box's manifest claims — a renamed checkout's old name, a deleted project — removing them only with `--force`. A missing manifest, or one older than 7 days (`FLAKELAB_STATE_GC_MAX_AGE_DAYS`), aborts the collection: a box that has not synced may hold slugs its manifest never recorded. Before this, the sync had no notion of deletion and an orphaned slug replicated forever.
- `flakelab backup --revisit-keeps` (backup and `--state-only` runs): re-holds findings settled as `keep` so the next `--review-secrets` offers them again — without it a keep was a one-way door with no supported path back. Revisited records stay excluded from the sync throughout.
- `flakelab backup --state-only`: both legs of the state root and nothing else — the merged history (read from the LIVE `~/.zsh_history`, since this mode never writes the payload's instance copy), Claude memory and, with `stateTranscripts`, transcripts, pushed AND pulled in one run. No payload copy, no rollback snapshot, no restore of activation-owned files. The pull leg skips any local transcript modified in the last 10 minutes: a live session appends through an open fd, and the rename-in-place a pull uses would orphan that inode and silently drop the session's tail. Until now nothing ever pulled outside a manual `--restore`, so with two machines pushing the state root was a write-only archive.
- `flakelab.stateSyncInterval` (default `null`): schedules `--state-only` on its own systemd user timer (`flakelab-state-sync`, `Nice=10`, `IOSchedulingClass=idle`) at the given `OnUnitActiveSec` span, e.g. `"30min"`. Needs `stateRoot` and `backupAutostart`. The full backup stays on its 24h timer — putting THAT on a short interval would re-snapshot the payload every run and burn the 5-deep rollback ring down to hours.
- `flakelab doctor` reports secret-gate findings held back from the state root — count, the transcripts held back whole (a held file with no synced copy at all never reaches the other machines), and the `--review-secrets` pointer. The gate's own warnings go to a journal nobody reads once the sync runs from a timer; without this the hold is invisible from the operator's seat. The doctor wrapper now exports `FLAKELAB_STATE_ROOT` for the whole-held probe.

## [0.2.0] - 2026-08-28

### Added

- `bwu` / `bwl` shell functions: `bwu` unlocks the Bitwarden vault on the TTY and parks the session token in mode-600 `~/.config/tyc/bw-session`; every shell exports it as `BW_SESSION` from there, so agents inherit an unlocked `bw` without the token crossing a command line or a transcript. `bwl` locks and removes the file. The token is per-unlock, so it lives outside `secrets.env` and outside `flakelab backup`.
- `flakelab.target` (default `wsl`): the platform a system is built for, and the module set in `nix/targets/` that goes with it — `wsl` is the NixOS-WSL distro, `proxmox-vm` a Proxmox guest. It rides outside `userData` (`mkSystem { target = "proxmox-vm"; userData = { … }; }`, or as a top-level key of the legacy attrset) because `imports` cannot be conditional: the choice is made before the module system runs, which is also why the option is read-only afterwards.
- `nixosConfigurations.proxmox-vm`: the tracked placeholders on the new target — cloud-init for the hostname, network and keys PVE hands the guest, a qemu-guest-agent that refuses fs-freeze so `vzdump` does not wait for a thaw that never comes, the cloud-init CLI a wrong boot is read with, keys-only sshd, and a root filesystem that grows into whatever disk it is given — on the virtio controllers the initrd can actually see.
- `flakelab.flakeAttr` (default `"default"`): the `nixosConfigurations` attribute `flakelab update` switches into, for an overlay flake that declares more than one box.
- `checks.targets`: `nix flake check` instantiates both systems and builds neither, asserting that each one carries its own platform and none of the other's.
- `flakelab.backupRoot` (default `null`, resolving to `${repoPath}/files/config` as before): the `flakelab backup` payload root, for a target with no Windows mount to point it at instead.
- `test-flakelab-cli`: the sixth offline suite, covering the router's target gate.
- `.#proxmoxImage`: the Proxmox seed image (`nix build .#proxmoxImage` → a qcow2), built as the `proxmox-vm-seed` variant of `nixosConfigurations.proxmox-vm` with `home-manager.users` forced empty — a full closure is 7.9 GiB, which no release asset carries, and a generic image has none of the credentials its activation would want. `checks.targets` asserts the stripping held.
- `flakelab-bootstrap`: the one-shot unit on the `proxmox-vm` target that turns a seed into your box. It reads `/etc/flakelab/bootstrap.env` — `OVERLAY_URL` (required), `OVERLAY_REF` (`main`, a branch or tag), `OVERLAY_ATTR` (`default`), `BOOTSTRAP_USER` (`flakelab.username`), `REPO_PATH` (`~<user>/git/flakelab-config`), `OVERLAY_SSH_IDENTITY` (`~/.ssh/<first sshKeys entry>`), `OVERLAY_KNOWN_HOSTS` (unset: `StrictHostKeyChecking=accept-new`), with a leading `~/` in the three paths resolved against the home passwd gives `BOOTSTRAP_USER`, because systemd reads the file itself and a `#` only starts a comment at the start of a line — clones the private overlay as that user and switches the system into `#<OVERLAY_ATTR>` as root. A missing identity exits 75 and names the path instead of failing the boot; `/var/lib/flakelab/bootstrapped` keeps it to one run and `journalctl -u flakelab-bootstrap` is the log.
- `.github/workflows/release.yml`: a `v*` tag builds the seed, compresses it with `qemu-img convert -c` and uploads `flakelab-proxmox-vm-<tag>.qcow2` plus its `.sha256` to the release, so an adopter's hypervisor pins an asset URL by tag rather than building the image itself.
- `nix-overlay-generate --target <wsl|proxmox-vm>` (default `wsl`), and the matching `target:` key in `user_data.yaml`: generates a `proxmox-vm` overlay with `target = "proxmox-vm";` first in the attrset and `windowsUsername` left out entirely, instead of hand-editing the flake a bare scaffold produces. An unknown value is refused up front rather than reaching `mkSystem`'s own `throwIf` with a generated file name in the error instead of the config the operator has open. Generating for `wsl` (the default, and what every existing config still selects) is unchanged byte for byte.

### Changed

- `flakelab.windowsUsername` is optional and defaults to `null`. It feeds the zsh jump out of the Windows profile directory, which only the `wsl` target has, so an overlay for any other target leaves it out.
- `nix/configuration.nix` is the system layer every target shares; the NixOS-WSL settings, the interop hazard note and `system.stateVersion` live in `nix/targets/wsl.nix`.
- `flakelab <command>` refuses the four WSL-only verbs (`provision`, `build-distro`, `test-provision`, `distro-name`) with exit 2 on any target other than `wsl`, and drops them from `--help` and its did-you-mean suggestions.
- `flakelab doctor`'s WSL interop check runs only when the target is `wsl`; every other target gets a single `ok` line instead of a spurious failure.
- `flakelab backup`'s per-instance path resolves `WSL_DISTRO_NAME`, then `FLAKELAB_INSTANCE` (exported by the nix wrapper from `hostName` on any non-`wsl` target), before falling back to the `wsl.exe` probe.
- `BROWSER` is set only on the `wsl` target (`wsl-open` needs a Windows default browser to hand a URL to); other targets' CLIs print the URL themselves.
- `flakelab.mcpPlaywright`'s server registration, and Claude's Playwright MCP bridge env, are gated on the `wsl` target too — extension mode's Windows Chrome path is meaningless elsewhere; a trace warns when `mcpPlaywright` is set on another target.
- `~/.claude/CLAUDE.md`'s managed block is now a target-neutral core plus a per-target file (`target-wsl.md` or `target-proxmox-vm.md`), so a Proxmox guest gets its own facts instead of a WSL box's `/mnt/c` and WSL-verb notes.

## [0.1.0] - 2026-08-27

First tagged release. The project has been in daily use on two machines since
before the public flip; this marks the point where adopters get a version to
pin to instead of a moving `main`.

### Added

- `flakelab.stateRoot` / `stateTranscripts` options for a shared state root synced across machines.
- A secret gate in front of the state root, reviewable with `flakelab backup --review-secrets`.
- The `flakelab` CLI, a single router binary for all subcommands, with deprecation shims for the old command names.
- `flakelab.claudeAgentDefaults` (default `false`): opt-in for the agent-box Claude Code settings — auto permission mode with its consent flag, Remote Control at startup, and removal of the four env vars that would defeat it.
- `flakelab.claudeOutputStyle` (default `null`): the Claude Code output style asserted into `settings.outputStyle` on every activation, so a style survives a fresh box instead of living in a git-ignored `settings.local.json`. Null leaves the key alone.
- `flakelab.claudeMdExtra` (default `""`): personal workflow rules appended inside the managed block of `~/.claude/CLAUDE.md`, after the neutral text this repo ships.
- `flakelab.hostName` (default `flakelab`): sets `networking.hostName`, which nothing set before — every box came up as `nixos`. An existing box is renamed at its next update, effective at the next distro restart, and anything keyed on the hostname sees a new machine: the gate ledger does, so already-applied holds are offered once more after the rename. Set `hostName = "nixos"` in the overlay to keep the old name.
- `setup-wsl-nix.ps1 -RestoreInstance <name>`: names the backup instance the overlay-payload restore reads, for a distro whose payload was written under another distro name. A name the payload has no directory for is refused, listing the ones it has.
- `setup-wsl-nix.ps1 provision` on a fresh PC — no overlay, no `-Config`, an interactive console — asks for the four values a config cannot do without (Linux user, git name, git mail, profiles; an optional repo list last) and writes them as `<overlay>\files\config\user_data.yaml` before carrying on; that file is found on every later run, so `-Force` regenerates from it. The README bootstrap is one command. Non-interactive runs and `-DryRun` keep the refusal; the `.cmd` menu's config prompt now falls through to the questions on Enter.
- `BACKLOG.md`: planned work, tracked in the repository alongside the code it describes rather than in the GitHub issue tracker.
- `flakelab.kiroTrustAll`, `flakelab.claudeTrustAll` and `flakelab.mcpPlaywright` (all default `false`): the operator's full-trust agent surface is now opt-in. Adopters no longer inherit `kk` (`kiro-cli chat --trust-all-tools`), `cc` (`claude --dangerously-skip-permissions`), `cli.json`'s `chat.disableTrustAllConfirmation`, or a browser-driving MCP server. Trust-all outranks the Kiro agent's `deniedCommands`, so the destructive floor does not apply under it — which is why it is a decision and not a default.

### Changed

- `flakelab update` bumps the flakelab input whatever its shape — a remote pin moves to its latest commit instead of needing `nix flake update flakelab` by hand. A local flakelab input is named rather than silently re-locked: `flakelab update` says which checkout it built from, and `flakelab doctor` warns on `path:`/`git+file:` inputs.
- `setup-wsl-nix.ps1 provision` with a config that carries no token (what the first-run wizard writes) skips the credential-copy prompt and the per-name "not in user_data.yaml" lines; the missing SSH key / secrets.env note reads as optional, with `flakelab update` as the way to enable the deferred steps later.
- `flakelab backup --restore` is now additive: it no longer deletes local files the backup does not have.
- `flakelab.bitwardenServer` defaults to `null`, which skips the `bw config server` activation entirely; set it to name a region.
- `files/config/claude/CLAUDE.md`, shipped verbatim into every `~/.claude/CLAUDE.md`, is reduced to facts about the distro; the workflow rules moved to `claudeMdExtra`.
- `flakelab doctor` skips its GitLab checks (token, `glab auth`, the SSH probe) when the overlay configures no `gitlabGroups`, `repos` or `kiroPluginRepo`.
- `setup-wsl-nix.ps1 provision` / `bootstrap` / `generate` now refuse when there is no overlay and no `-Config`, instead of provisioning this repo's placeholder identity. `status` still reports the fallback, and the `setup-wsl-nix.cmd` menu asks for a config path.
- A config that names only `repos:` — no `profiles:`, no `gitlab_groups:` — is accepted by both overlay generators, for adopters with no GitLab.
- The managed `permissions.deny` floor denies every force push and remote-branch deletion, not only those naming `main`; `worktree.baseRef` is no longer asserted.
- The agent instructions file is `AGENTS.md`, and it is the only one: the repo ships no root `CLAUDE.md`. `ARCHITECTURE.md`'s "Known gaps" moved into `known-issues.md` as "Known limitations".
- Every third-party `pre-commit` hook is pinned to an immutable commit SHA (`rev: <sha>  # frozen: <tag>`) rather than a mutable tag, which a compromised maintainer can repoint without changing the version string.
- `@jarahkon/hass-mcp-server` is version-pinned like the other MCP servers; it was resolved fresh by `npx --yes` on every start while holding a live `HASS_TOKEN`.
- Renovate waives `minimumReleaseAge` and automerges `@playwright/mcp` alone: the Playwright MCP Bridge Chrome extension auto-updates and cannot be pinned, so a lagging server is rejected with "unsupported protocol version" and a release-age hold is a guaranteed outage window. Every other package keeps the repo-wide hold.

### Removed

- `HANDOVER.md` and every pointer to it; open work is tracked in `BACKLOG.md`.

### Fixed

- A plugin named in `flakelab.claudePlugins` is now enabled as well as installed (`plugin enable` exits 1 once a plugin is enabled, so that case is not reported as a failure). Claude Code loads a plugin only when `settings.enabledPlugins` names it, and `plugin install` leaves that key alone, so a plugin disabled once stayed inert on every later rebuild — its MCP servers and agents missing from sessions while activation reported success. Opting out is still dropping it from `claudePlugins`, which uninstalls it.
- `setup-wsl-nix.ps1` no longer dies on a native command's stderr: under `ErrorActionPreference = 'Stop'` Windows PowerShell 5.1 turns a redirected stderr line into a terminating error, and wsl.exe's transient "Failed to start the systemd user session" right after the first switch killed the provision at the interop probe. Probe-style native calls now run through `Invoke-NativeQuiet` — including the `git ls-files flake.lock` check before switch 1, which aborted a migration whose overlay does not track its lock.
- An unattended `migrate` now writes its completion marker.
- `gitpublisher`'s secret gate survives a large hook report: it read the report through a pipe, where `grep -q` closed it at the first match and `pipefail` turned the resulting SIGPIPE into "no secret found", reporting a real leak as a lint stop. The same report also broke the JSON verdict, since one argv element caps at ~128 KB and it was passed to `jq --arg`.
- `setup-wsl-nix.ps1` refuses a `#` in the checkout or overlay path (the flake-ref fragment delimiter, so `--flake <path>#default` was cut at it) and skips a key filename containing a single quote instead of copying the wrong file.
- The four Claude activations that write `~/.claude/settings.json` (settings policy, statusline, Playwright env, WhatsApp env) are gated on `installClaude`, so a box without Claude Code no longer gets a settings.json.
- `cloneExclude` entries are ERE-escaped and shell-quoted before reaching `grep`, and a grep failure aborts instead of yielding an empty clone list.
- `flakelab backup --restore` recreates `~/.kube` 0700 with 0600 files, and no longer creates it at all under `--dry-run`.
- `path:` flake URLs are percent-encoded, so a checkout or overlay under a path containing a space (`C:\Users\First Last\git\`) builds instead of failing every rebuild.
- `flakelab update` re-locks a `path:` flakelab input before the switch, so a rebuild after a `git pull` no longer evaluates the previously locked snapshot of the flake.
- Flow-style YAML lists (`profiles: [a, b]`) are parsed as lists by both overlay generators, instead of reaching the overlay as a literal string.
- `gitpublisher` no longer reads pre-commit's cold-cache "Installing environment for .../gitleaks" line as a secret finding.
